**改动文件**：
- `scripts/h2-sentinel/doctor.mjs`、`scripts/h2-sentinel/launch.mjs`（仅按演练暴露问题做加固）
- `submission/h2-sentinel/OPERATOR_RUNBOOK.md`（失败项闭环表+排障节）
- `submission/h2-sentinel/RUNTIME_EVIDENCE_CHECKLIST.md`（演练记录追加节）

**实现要点**：
1. 演练环境定义：非本开发机，或本机新建 Windows 账号；无 node_modules/venv/缓存残留；官方数据按 runbook 拷贝到指定绝对路径

## D-P0-2 submission 16 字段导出收口

**目标**：test 分区 CSV 导入 → 16 字段全量导出全绿：易漏四字段（`confidence`/`evidence_json`/`first_detection_time`/`requires_human_confirmation`）在 check-submission.mjs 升级为**硬门禁**（缺列/空值/类型非法即 FAIL，非 WARN）；导出样例留痕。

**背景**：验收-T12 要求导出合规；官方模板 `D:\allcode\h2-t01-official\dataandfiles\17_submission_template.csv` 16 列全部必填。历史经验：后加的四字段最易漏——plan0829 已有防御导出，但门禁强度需复核为硬 FAIL。severity/subtype 语义自 plan0830 起由 A-P0-3 确定性映射收口（severity=C 码唯一映射：C01/C06=中，C02/C03/C04/C05/C07=高），导出侧必须消费同一映射，避免两套口径。

**改动文件**：
- `services/h2-analytics/src/h2_analytics/reports/submission.py`（导出器）
- `validation/check-submission.mjs`（校验器主改动）
- 必要时联动 `validation/lib/submission.mjs`、`validation/lib/official-contract.mjs`

**实现要点**：
1. 校验器对照官方表头**逐字断言** 16 列名与顺序（表头常量取自官方模板原文，README §1.7）
2. 易漏四字段硬门禁：非空+类型合法——confidence ∈ [0,1] 数值；evidence_json 可解析 JSON 且含结构化键；first_detection_time 与 start_time 同构格式；requires_human_confirmation ∈ {0,1}
3. severity/subtype 从 A-P0-3 确定性映射取值——**只消费不重算**；映射源经 CONTRACTS 引用，A 线变更自动跟进重跑
4. token 归一化校验保持绿：affected_equipment 对台账 `PV01/BESS01/PCC01/EMS01/ELZ01-03/AUX01`，引用 `submission-equipment-tokens.json`（冻结契约，只读）
5. 负样本自测：人为构造缺列/空值/类型错样例，断言逐项 FAIL；正常样例断言零误报
6. test 分区导出样例（CSV+check-submission 输出）留痕入 RUNTIME_EVIDENCE_CHECKLIST
7. 新增断言 <100 行纪律；不破坏 plan0829 既有绿灯禁项

**验收**：
- `node validation/check-submission.mjs` 对 test 分区导出产物全字段绿（含四字段硬门禁）
- 负样本三类（缺列/空值/类型错）逐项 FAIL 清单；正常样例零误报
- 导出样例与校验输出入库留痕（模板见 §0.4）

**服务验收条款**：验收-T12 导出（+submission 契约防御）

**会话数**：1 会话（1d）

**依赖**：A-P0-3（软依赖：映射未合入前先用现行导出值收口门禁，映射合入后回归一次）

**裁剪位**：P0 不可裁；最低保底=四字段硬门禁+一次 test 导出留痕

**风险回退**：校验过严致正常导出 FAIL→逐字段比对 plan0829 冻结导出样例定位差异；映射消费冲突→以 A 线 anomaly-taxonomy.json 为准并在 CONTRACTS 登记口径

## D-P1-1 一键启动加固

**目标**：`npm run h2:fixture` / `npm run h2:local` 失败模式加固：**本机 10 连启动 100% 成功 + 5 项故障注入均有自愈或明确指引**。

**背景**：验收-T13 的组织方独立环境不会给第二次机会。已知失败模式四类：端口占用（5173/8765 被残留进程或他程序占）、依赖缺失（npm/venv 未装全即启动）、首跑缓存（首次构建慢/缓存目录缺失被误判挂死）、残留进程（上次未干净退出）。现有 `adversarial-launch.mjs` 与 `launch.test.mjs` 已有故障注入底座，扩展而非重造。

**改动文件**：
- `scripts/h2-sentinel/launch.mjs`（前置检查+自愈）
- `scripts/h2-sentinel/smoke.mjs`（联动）
- `scripts/h2-sentinel/doctor.mjs`（检查项扩展）
- `scripts/h2-sentinel/adversarial-launch.mjs`、`launch.test.mjs`（注入场景扩展）

**实现要点**：
1. 启动前置检查：端口占用→给出占用 PID 与 kill 指令（或 `--force` 自动清理，默认仅提示不动手）；依赖缺失→指明缺失项与安装命令；残留进程→检测并提示
2. 首跑缓存：首跑慢属预期，启动日志明示当前阶段与预计耗时，避免被误判挂死
3. 5 项故障注入逐项验证「自愈或 RUNBOOK 指引」二选一成立：端口占用×2（5173/8765）、依赖缺失、缓存破坏、残留进程
4. 10 连启动脚本化：循环起停计数，输出成功率清单留痕（不进 git 的输出按 §0.4 留摘要）
5. `start-h2-sentinel.bat` 无 `--mode` 参数时的报错改为友好提示（必须带 --mode fixture/local）
6. doctor 扩展的检查项与 RUNBOOK 排障节一一对应（README §5.1 速查表同步更新）

**验收**：
- 10 连启动成功率 100% 清单留痕（fixture 与 local 双模式各一轮）
- 5 项故障注入逐项结果表（注入方式→系统行为→恢复方式）入库
- doctor 扩展项全绿；bat 无参提示友好

**服务验收条款**：验收-T13 部署复现

**会话数**：2 会话（1.5d：加固实现 1 + 注入与连启验证 0.5）

**依赖**：无

**裁剪位**：裁剪序位 3——降级为 doctor 扩展（增补端口/进程/依赖检查+RUNBOOK 排障节，不做自动化连启与注入）

**风险回退**：加固改动引入新破坏→launch.mjs 逐项 git 还原至 p3-base 版本，只保留 doctor 检查项（纯增量不回退）

## D-P1-2 验收-T02 质量扩展（plan0829 P2-6 承接）

**目标**：数据质量门禁三类扩展：**枚举合法性**（run_state ∈0-3 / available_flag ∈0-1 / plc_heartbeat ∈0-1）、**单位与中文描述跨文件一致**（以变量字典为单源）、**跨文件引用一致**（设备名/变量名引用无悬空）；3 类脏样例全检出+正常数据零误报。

**背景**：验收-T02 要求导入数据质量检查；验收-T01 要求导入维护。plan0829 只做了基础结构校验（P2-6 遗留）：枚举值越界、单位描述在字典与前端两处漂移、跨文件引用悬空均不报。run_state 语义（0停/1待/2运/3降额）是 C02 等检测的输入，脏值若静默放行会污染下游。

**改动文件**：
- `services/h2-analytics/src/h2_analytics/quality/checker.py`（枚举+一致性检查）
- `services/h2-analytics/src/h2_analytics/ingestion/csv_loader.py`（导入路径挂钩）

**实现要点**：
1. 枚举检查进 checker.py：三枚举字段的合法值集合+违规行号+违规值采样上报（不整读大 CSV，流式逐块检查）
2. 单位/中文描述一致性：以 `fields.json`（冻结契约，只读）为单源，校验质量报告与导入元数据中出现的单位/描述与之一致；发现不一致→报告差异并走 change-request 改漂移方（D 不改 fields.json）
3. 跨文件引用：设备名限定台账集合（PV01/BESS01/PCC01/EMS01/ELZ01-03/AUX01），变量名限定字典 69 列集合
4. 脏样例三类各造最小 CSV（枚举越界/单位漂移/悬空引用），断言全检出；正常样例断言零误报
5. 质量问题**前端可见路径**：质量报告结构经 api 契约暴露，展示归 C 线——对接点写 CONTRACTS（字段清单+C 线承接卡号），本卡只保证数据与接口形状
6. 新增断言 <100 行纪律；pytest 全绿

**验收**：
- 3 类脏样例逐项检出清单；正常数据（train 采样）零误报
- pytest 绿；CONTRACTS 登记 C 线对接点

**服务验收条款**：验收-T02 数据质量 + 验收-T01 导入维护

**会话数**：2 会话（1.5d：checker 扩展 1 + 一致性与 C 线对接 0.5）

**依赖**：无

**裁剪位**：裁剪序位 2——降为枚举校验（只做三枚举门禁；单位/跨文件一致性转 R3 或明示放弃）

**风险回退**：校验过严阻断正常导入→该检查项降级为 WARN 并在质量报告标注（不静默删）；与 C 线对接延迟→先冻结接口形状文档，展示后补
